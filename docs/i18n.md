# Languages

Takeback's UI was written in French, with the French strings used directly as
display text. This document records what the translation layer does today, what
it deliberately does not do yet, and what translating the rest actually costs.

## How it works

`app/i18n.py` is the whole mechanism — no gettext, no Babel, no compiled
catalogues, because the app ships as one container and a translation here is a
few hundred short strings.

- **Keys name the role, never the text.** `nav.imports`, not `"Imports"`. The
  key is looked up in `CATALOGS[locale]`.
- **The fallback chain is default locale, then the key itself.** A key with no
  entry shows *as the key* rather than as a blank: a missing translation should
  be visible in the UI, not silently render an empty button. It is also why a
  partially filled locale is safe to ship — nothing disappears.
- **The locale is resolved once per request**, in the middleware in
  `app/main.py`, and held in a `ContextVar` for the duration. `?lang=` wins for
  a single request, then the `tb-lang` cookie, then the browser's
  `Accept-Language` (honoured in its own order of preference, with `q=0` read as
  a refusal), then `TAKEBACK_LANG`, then `fr`.
- **`set_locale` / `get_locale`** are what a test or a script uses to pin a
  language without a request.

`templating.py` exposes it to Jinja as `_()`, `view_label(view)` and
`export_hint(platform)`; `display_label` consults `i18n.type_label` before the
importers' own label, so an item type gains a translation without its importer
being touched.

## What is translated today

| Surface | State |
|---|---|
| App chrome (`templates/base.html`): sidebar, topbar, search field, theme and privacy buttons, `<html lang>` | **French and English** |
| Dashboard tab names (`app/platforms.py`, the `View` constants) | **French and English** |
| "Where to ask for your export" hints (`Platform.export_hint_key`) | **French and English** |
| Item type names (`app/i18n.py`, `TYPE_LABELS`) | English for the common types; anything absent falls back to the importer's French label, then to `humanize(item_type)` |
| Page bodies (`home.html`, `imports.html`, `browse.html`, every `templates/platform/*.html`) | **French only** — the bulk of the remaining work |
| Chart labels and legend strings built in `static/app.js` | **French only** |
| Labels written by `app/stats.py` (`"Dépenses dans le temps"`, `"Non renseigné"`, the purchase dimensions…) | **French only** |
| The label/value pairs stored in `items.fields_json` | **French only, and they are data — see below** |

So `TAKEBACK_LANG=en` (or a browser asking for English) gives an English shell
around French page bodies. That is a partial translation, on purpose, and it is
the honest state of this pass: the mechanism is finished and tested, the
catalogue is not full.

**The default is `fr`**, so nobody meets a half-translated interface unless they
ask for one.

## The part that is not a translation job

The label/value pairs an importer produces are stored in `items.fields_json`
(e.g. `{"Appareil": "Kindle", "Pages tournées": "42"}`), and `app/stats.py` and
`app/crud.py` read them back **by those French labels**:

```python
stats.py:1129   fields.get("Montant")
stats.py:1130   fields.get("Quantité")
stats.py:1741   fields.get("Entreprise")
stats.py:2000   fields.get("Fin")
stats.py:425    fields.get("Appareil")
stats.py:428    fields.get("Pages tournées")
stats.py:675    fields["Département"]
crud.py:444     fields.get("Document")
```

The French label is therefore **both a display string and a logic key, and it is
already written into every existing database**. Renaming one is not a
translation: it is a data migration, and a half-done one corrupts stored data.

That migration, when someone takes it on, is: introduce a stable key per field,
write both keys for a transitional period (or migrate `fields_json` in place,
with a backup), move the `fields.get(...)` call sites to the new key, then drop
the label from the catalogues. It belongs in its own change, with a test that
reads a pre-migration database, not in a pass that also renames everything else.

## What remains, and roughly what it costs

1. **Page bodies and chart labels** — mechanical, no design decisions: lift each
   French string into a catalogue entry and render it through `_()`. Touches
   `templates/` (~3,900 lines) and `static/app.js`. The largest chunk by far,
   and the one that makes the UI feel genuinely translated.
2. **`app/stats.py` labels** — the dimension names and "Non renseigné" are
   computed at render time (unlike `fields_json`), so these are plain
   translations.
3. **The stored label/value keys** — the migration described above.
4. **Number and date formatting.** `templating.number`/`money`/`date_fr` are
   French by construction (narrow no-break space as the thousands separator, a
   decimal comma, `dd/mm/yyyy`). An English locale should switch them
   (`1,234.56`, `mm/dd/yyyy`), or the locale should carry its own formatters.
   Currently they are locale-independent, so an English UI still formats numbers
   the French way.
5. **A language switch in the UI.** The `tb-lang` cookie and `?lang=` parameter
   are read, but nothing sets them yet — a small picker in the sidebar footer
   would do it.

## Adding a language

1. Add the locale to `LOCALES` and a catalogue to `CATALOGS` in `app/i18n.py`.
2. `tests/test_i18n.py::test_every_key_exists_in_every_catalogue` fails until
   every key the other catalogues have is present (or deliberately translated to
   the same string), which is the point.
3. Add it to `TAKEBACK_LANG`'s documented values in the README.
